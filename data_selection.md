## 1. Project Goal

**Problem.** Detect fraudulent mobile-money transactions in a large stream of mostly legitimate ones, while keeping false alarms low.

**Research question.** How effectively can distributed machine-learning models (Logistic Regression and Random Forest on Apache Spark) detect fraudulent transactions while keeping the false-positive rate low, and how do accuracy and runtime change as the data grows?

**Why it is worth investigating.**
- **Fraud is rare, so "accurate" models can be useless.** Only 0.129% of transactions in our data are fraud. A model that labels everything legitimate is 99.87% accurate and catches nothing. Evaluating models properly (PR-AUC, recall at a fixed false-positive rate) is the real problem.
- **False alarms have a cost.** Every flagged transaction is reviewed by an analyst or blocks a real customer. A detector is only usable if it keeps false positives low.
- **The data volume needs distributed processing.** Mobile-money services process millions of transactions a day. Detection has to scale with data size, which is why we use Spark and measure scalability explicitly.
- **Real financial data is private.** Synthetic but realistic datasets such as PaySim are among the few ways to study this openly (see Data Sources).

## 3. Dataset Description

### Contents
Every record is one mobile-money transaction: who sent money, who received it, how much, the balances before and after, and whether it was fraud. The fraud modelled is **account takeover**: a fraudster takes control of a customer's account, transfers the funds to a "mule" account, and cashes them out.

### One dataset or several?
We integrate **four files from two sources** (real PaySim and our synthetic generator) in **two formats** (CSV and JSON) into one Spark table with added `source` (real or synthetic) and `month` columns. All four share one schema. Section 4.3 explains why that is a deliberate choice, and its limits.

## 4. Analysis of the 5 Vs

### 4.1 Volume

**[Present] Size.**
- 12,725,240 records in four files: 2.12 GB uncompressed, 0.47 GB zipped.
- The original Kaggle file alone is 6.36 million records (494 MB).

**[Present] Evidence that size causes real processing problems:**
- **The JSON format is about 3× larger for the same data.** The same 3,181,310 records take 249.5 MB as CSV but 784.3 MB as a JSON array, because every record repeats every field name.
- **The JSON files cannot be split for parallel reading.** A JSON array must be parsed as one document (Spark's `multiLine` mode), so one task has to read each 800 MB file alone. The gzip-compressed copies are not splittable either.
- **Simple in-memory processing already fails.** While checking our split, loading the original file and both halves into Python together exceeded 7 GB of memory and the process was killed. We had to rewrite the check to stream through the files row by row.
- **Some steps multiply the work.** Grouping per customer or per hour, joining sources, and 3-fold cross-validation over a hyper-parameter grid each repeat passes over millions of rows.

**[Present] Data can grow on demand.** Our generator produces any number of additional months or records with the same statistical shape. This lets us test the system at 10×, 100× or more without finding new data.

**Infrastructure and how we use the full data.** *[Present]* The environment is set up and validated: on 2026-11-27 our test notebook (`notebooks/00_environment_check`) passed 8/8 checks on Databricks serverless compute (Spark 4.2.0), reading all four files and building the shared 12,725,240-row table (see `docs/environment.md`). *[Planned]* the remaining items below.
- **Processing engine:** Apache Spark (PySpark DataFrames, Spark MLlib).
- **Platform:** Databricks Free Edition, a serverless Spark workspace that stores the files in a Unity Catalog volume. A local Spark installation is used where we need control over the number of cores.
- **First step:** convert every raw file once into a columnar, splittable format (Delta/Parquet), partitioned by `source` and `month`, so all later stages read in parallel.
- **Full data:** we analyse all 12.7M records. Scalability tests also run on stratified fractions (10%, 25%, 50%, 100%) and on generated data larger than the current total.

**Challenges as the size grows:**
- Single-task parsing of JSON.
- Shuffles during grouping and joins.
- Memory pressure when collecting results to the driver; we avoid this by computing evaluation curves as Spark aggregates.
- Training time for Random Forest and cross-validation.
- The daily compute quota on the free platform.

### 4.2 Velocity

**[Present] How the data was generated.**
- Each dataset is a static, one-time snapshot. The Kaggle file was published once and has no update schedule.
- *Inside* the data, transactions arrive **hour by hour** (`step`), very unevenly:

| Measure | Real data (A) |
|---|---|
| Records per hour, median | 529 |
| Records per hour, peak | 51,352 |
| Average records per day, days 1–17 | 352,201 |
| Average records per day, days 18–31 | 26,800 |

- Fraud arrives at a steady 274–375 records per hour of the day, while legitimate traffic follows a strong daily cycle.

**[Present] New data can be added.** Synthetic month 2 continues the timeline at hour 744. It is a realistic stand-in for "next month's data arriving", and the generator can produce further months.

**[Planned] System design.**
- **Batch training:** models are trained in batch on historical data (month 1). Batch is sufficient for model building and evaluation.
- **Simulated streaming:** month 2 is replayed hour by hour as micro-batches with Spark Structured Streaming. Each new file arriving in storage is picked up, appended to the table and scored with the trained model. This mirrors how fraud scoring works in practice: decisions are needed within seconds of a transaction.
- **Per-batch throughput** (records scored per second) will be measured to show whether the design could keep up with the observed peak of about 51k records per hour.

### 4.3 Variety

**[Present] Formats, structures and sources.**

| Aspect | What we have |
|---|---|
| File formats | CSV (files 1 and 3) and JSON arrays (files 2 and 4) |
| Structure | Structured tabular records. The JSON files are semi-structured documents whose records happen to be flat. |
| Sources | (A) real PaySim from Kaggle; (B) our own synthetic generator |
| Number formatting | The CSV files store large values in Java scientific notation (for example `1.04197848E7`); the JSON files store plain numbers (`10419784.8`). |
| Behaviour | The real and synthetic data follow different rules (see Veracity): the real data has inconsistent balances, while the synthetic data has consistent balances and returning customers. |

**What each source contributes.**
- **(A) Real PaySim** is the reference data, calibrated from real transaction logs. It is used for the main training and evaluation.
- **(B) Synthetic data** contributes a second, independent month of activity for testing on later data, a source with different behaviour for testing generalisation, and unlimited extra volume for scalability tests.

**[Planned] How the system handles these formats.**
- Each format is read with an explicit schema: CSV with a header, JSON with `multiLine` enabled.
- Types are normalised, and `source` and `month` columns are added.
- Everything is unioned into one Delta table with one schema.
- The `step` values of the real data and synthetic month 1 overlap (both cover 1–743) but describe different simulated worlds. So `step` is never used as a key across sources; `source` + `step` is.

**Honest assessment and possible extension.**
- All four files share one schema, so the integration challenge comes from formats, layouts and data behaviour, not from combining different kinds of information.
- **[Possible extension, not yet committed]** A second public source with a different schema could be added. One option is BankSim, card payments simulated by the same research group, with customer age, gender and merchant category. That would require real schema alignment and could test whether findings carry over between payment systems.

### 4.4 Veracity

**[Present] Trustworthiness of the source.**
- Dataset A comes from a peer-reviewed simulator (EMSS 2016) with public source code, and is calibrated on real logs.
- It is **synthetic**: its realism is limited by what the simulator models. Its own documentation warns that fraudulent transactions are cancelled, and that the balance columns should therefore not be used for fraud detection.

**[Present] Quality issues we measured in the full real file (6,362,620 records):**

| Issue | Evidence | Effect on analysis |
|---|---|---|
| Extreme class imbalance | 8,213 fraud records (0.129%), 774 legitimate per fraud | Accuracy is meaningless; we need class weighting and PR-AUC |
| Label leakage in `isFlaggedFraud` | 16 records, all fraud, all with an unchanged balance | Dropped before modelling |
| `isFlaggedFraud` contradicts its own definition | Documented as "transfer over 200,000", but only 16 of 409,110 such transfers are flagged | Confirms the flag is unreliable |
| Balances that don't add up | 56.6% of outgoing transactions are larger than the sender's balance | Balance features may reflect simulator quirks rather than behaviour |
| Missing balance information | Recipient balances are 0 for all merchant records (33.8% of rows) and for 3.9% of customer recipients, rising to 49.6% among frauds | A "zero balance" partly encodes how the simulator works, not real behaviour |
| Fraud almost always drains the account | 97.8% of frauds move the entire balance | Fraud may be unrealistically easy to detect, so scores may look better than they would on real data |
| Zero-amount fraud records | 16 fraud records with `amount = 0` | Odd records to inspect, keep or drop |
| One-time customers | 6,353,307 distinct senders in 6,362,620 records | Customer-history features are impossible on the real data |
| Uneven calendar | Volume falls about 13× after day 17 | A naive time-based split puts very different traffic in train and test |
| Number formatting | 261,365 rows contain values in scientific notation (`E7`) | Spark parses them correctly; naive string handling would not |
| Missing values / duplicates | 0 missing, 0 duplicate rows | No imputation needed |

**[Present] Our own validation of derived and synthetic data:**
- **Split halves (21/21 checks passed).** Row counts, every value in order, fraud, type and flag counts, sums and min/max all match. Most decisively, the original file was rebuilt **byte for byte** from the two halves, with an identical SHA-256.
- **Synthetic data (12/12 and 13/13 checks passed).** Same columns and types as the real file, no missing values, duplicates, negative balances or IDs shared with the real data or between the months. The fraud rate is 0.129%, and transaction-type shares and amount percentiles match the real data closely. For example, the median CASH_OUT amount is 146,947 in the real data and 146,626 in the synthetic.
- **Known bias in our synthetic data.** It is "plausible", not real. It deliberately differs from PaySim: balances always add up, customers transact about 3.3 times a month, and 9% of frauds take only part of the balance. Results on it must be reported separately and labelled synthetic.

**[Planned] Validation, cleaning and preprocessing.**
- Schema enforcement when reading.
- Dropping `isFlaggedFraud` and the raw IDs.
- A leakage audit: how well each single column predicts fraud on its own.
- An ablation **with and without the balance columns**, following the dataset authors' warning.
- Flags for inconsistent balances instead of silent "fixes".
- Reviewing the zero-amount records.
- Data-quality checks repeated automatically each time new data (month 2) arrives.

### 4.5 Value

**[Planned] Problem and beneficiaries.**
- **The problem:** flag likely fraudulent transactions early, with few false alarms.
- **Who benefits:**
  - Mobile-money providers and banks, which lose less money.
  - Fraud analysts, who review fewer, better alerts.
  - Customers, whose legitimate payments are blocked less often.
  - Researchers, through an open, reproducible pipeline on public data.

**Specific questions the system will answer:**
1. At a false-positive rate of at most 0.1% (100 false alarms per 100,000 legitimate transactions), what share of fraud can each model catch?
2. Does Random Forest beat the Logistic Regression baseline on PR-AUC, and is the gain worth the extra training time?
3. Which transaction patterns signal fraud (type, amount relative to balance, account draining, hour of day), and do the models still work **without** the balance columns the dataset authors warn about?
4. Does a model trained on month 1 still perform on month 2 (later data), and on data from a different source (real → synthetic)? How large is the drop?
5. How do training time and model quality change with data size (10% → 100% → generated data larger than the current total), and where does Spark's parallelism pay off?

**How we will judge whether results are useful:**
- PR-AUC as the main metric, against a random baseline of 0.0013.
- Precision, recall, F1 and false-positive rate at a threshold chosen on validation data, never on test data.
- A comparison with the "flag nothing" baseline, which shows why accuracy is misleading.
- Error analysis of missed frauds and false alarms by transaction type and amount.
- Runtime per million records for the scalability results.
- A result is **useful** if it gives an operating point a fraud team could realistically use: high recall at a false-alarm rate it can actually investigate.

## 5. Data Preparation

**Anticipated tasks:**
1. **Ingest.** Read the CSV files (header, explicit schema; scientific notation parses as double) and the JSON arrays (`multiLine`, explicit schema). Verify record counts against the checksummed source files.
2. **Convert.** Write each source once to Delta/Parquet, partitioned by `source` and `month`, so later stages read in parallel instead of re-parsing the JSON.
3. **Integrate.** Union the four files into one table with added `source` and `month` columns. Keep IDs as strings; the ID ranges of the sources never overlap (verified).
4. **Clean.** Drop `isFlaggedFraud`. Review the 16 zero-amount fraud records. Flag inconsistent balances rather than altering them. Document the 239/240 boundary between the two halves (hour 239 appears in both, with different records).
5. **Engineer features.**
   - Hour of day.
   - Log of the amount.
   - Merchant-recipient flag (from the `M` prefix).
   - Amount relative to the sender's balance.
   - Account-emptied flag.
   - Balance-error features, each in a version with and without the balance columns.
   - Per-customer history, possible only for the synthetic data, where customers repeat.
6. **Split without leakage.** Use a stratified train/validation/test split within month 1, plus a time-based test on month 2. All encoders, scalers and class weights are fitted on the training data only.
7. **Handle class imbalance.** Use class weights; compare with undersampling if time allows.

**Challenges we expect:**
- **Non-splittable JSON.** Parsing two 800 MB JSON arrays happens in a single task each, so it must be done once and cached as Delta.
- **Mixing data from different rules.** Real and synthetic records follow different behaviour, so a model trained on the mix could learn "which source" instead of "which fraud". We will always report results per source.
- **Leakage.** The balance columns and the rule flag can give away the label, so the leakage audit and ablation are required, not optional.
- **Imbalance.** 0.129% fraud means the test sets contain only a few thousand frauds, so metrics need confidence intervals or repeated splits.
- **Free platform limits.** The serverless compute quota can stop work for the rest of the day; heavy jobs (cross-validation, scalability runs) must be scheduled early.

## 6. Limitations and Risks

| Limitation | Type | How it may affect the project | Mitigation |
|---|---|---|---|
| All data is simulated: PaySim is calibrated on real logs, our data on PaySim | Representativeness | Fraud patterns are cleaner than in reality (97.8% of frauds drain the account), so scores may be overly optimistic | Report this explicitly; balance-column ablation; real-vs-synthetic transfer test |
| One country's mobile-money service, scaled to 1/4 | Representativeness | Results may not carry over to card payments, banks or other markets | Frame conclusions as "on mobile-money simulations"; possible second source (Section 4.3) |
| Known simulator quirks (inconsistent balances, one-time customers, uneven calendar) | Quality | Some features describe how the simulator works, not real behaviour | Documented in 4.4; flags instead of silent fixes |
| Our synthetic data was built by us | Quality / bias | Its realism depends on our design choices | Calibrated on real data; validation report; always labelled and reported separately |
| Static data, no live feed | Update frequency | Velocity is simulated (replaying month 2), not observed | Generator can produce further months; streaming design still exercised |
| One schema across all files | Variety | Integration covers formats and behaviour, not different kinds of information | Possible extension with a differently structured source |
| Size is moderate (2.1 GB) | Volume | Some steps would fit on one machine | Scalability tests on generated data well beyond the current total |
| Files exceed GitHub's 100 MB limit | Availability | Data cannot live in the repository | Scripts + checksums in the repo; shared team copy |
| CC BY-SA 4.0 share-alike | Licensing | Redistributed derivatives (the halves) must keep the same licence and credit | Attribution in all deliverables; we do not redistribute publicly |
| Free compute platform quotas and no service guarantee | Infrastructure | Jobs can be cut off for a day | Run heavy jobs early; local Spark as a fallback; keep a backup copy of the data |
